# AgentCare Patient Domain (Administrative)

This document describes the patient domain implemented in STORY-005: an
ADMINISTRATIVE patient record, tenant-scoped repository/service layer,
and a protected, tenant-safe API. It follows the same CURRENT vs. PLANNED
discipline as [ARCHITECTURE.md](ARCHITECTURE.md): everything described
here as implemented exists in the repository today; anything marked
PLANNED does not yet. See
[adr/ADR-0005-patient-identity-and-access.md](adr/ADR-0005-patient-identity-and-access.md)
for the decision record, and [RBAC.md](RBAC.md) for the identity/
authorization model this story consumes for the first time.

## 1. Administrative Scope (Healthcare Safety Boundary)

`Patient` (`app/models/patient.py`) is an **administrative** record only:
an identifier, a name, a date of birth, and tenant/identity linkage.
It deliberately holds **no** diagnosis, symptoms, medication, dosage,
treatment recommendation, clinical assessment, insurance/claims data,
clinical notes, or emergency-triage information — see
[ARCHITECTURE.md](ARCHITECTURE.md) Section 7 "Healthcare Safety
Boundary". Adding any such field to this model would be a scope
violation, not an incremental extension.

## 2. User vs. Patient

These are two separate concepts, deliberately not conflated:

- **`User`** (STORY-004) — a global authentication identity: email +
  password hash. Not scoped to any organization on its own.
- **`Patient`** (this story) — a healthcare organization's administrative
  record of a person, scoped to exactly **one** `Organization`.

A `Patient` MAY optionally be linked to a `User` via `Patient.user_id`
(Section 4) — but a `Patient` can exist with no linked `User` at all
(e.g. registered by front-desk staff before that person ever creates a
portal account), and a `User` can exist with no linked `Patient` anywhere
(e.g. every `ADMIN`/`STAFF` user). `User == Patient` is never assumed
anywhere in this codebase.

## 3. Patient Number

`patient_number` is the organization's OWN administrative identifier for
a patient (e.g. an MRN-style code) — supplied by the authorized
`ADMIN`/`STAFF` caller creating the record, not generated by this story
(no sequence/number-generation engine is built here; see Section 10).

- Unique only **within** its organization: `UNIQUE(organization_id,
  patient_number)`. The same number may validly appear under a different
  organization.
- Normalized minimally: surrounding whitespace is stripped. Deliberately
  **not** case-folded (unlike `User.email`) — organizations may use
  meaningfully-cased identifiers, and there's no equivalent of email's
  "same address, different case" login-friction problem to solve here.

## 4. User <-> Patient Linkage

`Patient.user_id` is OPTIONAL (nullable FK to `users.id`, `ON DELETE
RESTRICT` — no silent cascade-delete of a patient record if the linked
user is ever removed).

**Uniqueness**: `UNIQUE(organization_id, user_id)`, enforced at the
database level. Under PostgreSQL, `NULL` values are pairwise distinct for
a `UNIQUE` constraint's purposes, so this simultaneously guarantees:

- any number of patients with no linked user (`user_id IS NULL`) may
  exist in the same organization, and
- a given `(organization, user)` pair maps to **at most one** patient
  record.

A `User` MAY be linked to patient records in **multiple different**
organizations independently (each governed by its own row and its own
organization-scoped membership) — linkage in one organization has no
bearing on any other.

**Linkage validity** (who may `Patient.user_id` point at, and when) is
enforced at the **service** level
(`app.services.patient._validate_user_link`), not the database: linking a
`user_id` requires that user to have an **ACTIVE** `OrganizationMembership`
in the **same** organization with role `Role.PATIENT` specifically — an
`ADMIN`/`STAFF` user is not silently linkable as a patient. See
[adr/ADR-0005-patient-identity-and-access.md](adr/ADR-0005-patient-identity-and-access.md)
for why this is a service-level rule rather than a database constraint
(short version: a membership's role can change independently of any
patient row, so a hard DB constraint would need continuous
re-validation via a trigger — more schema machinery than this story's
scope justifies; a service-level check at creation time is simpler and
keeps the invariant in one readable place).

## 5. Tenant Ownership

`Patient.organization_id` is **mandatory** — every patient belongs to
exactly one `Organization`, matching every other tenant-owned entity
(see [DOMAIN_MODEL.md](DOMAIN_MODEL.md)).

`app/repositories/patient.py` has **no** `get_by_id(patient_id)` shape —
every read function requires `organization_id` explicitly
(`get_by_id(session, organization_id=..., patient_id=...)`). This is
deliberate: it is structurally impossible for a service or route to
"forget" tenant scoping, because there is no unscoped query to call by
mistake.

## 6. Repository & Service Layers (New in This Story)

STORY-005 introduces AgentCare's first real repository and service:

```
Route (API layer)
  -> PatientService (business rules, transaction ownership)
    -> app.repositories.patient (persistence/query only)
      -> AsyncSession
```

- **`app/repositories/patient.py`**: `get_by_id`, `get_by_user_id`,
  `get_by_patient_number`, `list_by_organization`, `create`. Adds,
  flushes, and queries only — never performs RBAC, never decodes a JWT,
  never owns HTTP concerns, and **never commits**.
- **`app/services/patient.py`**: `PatientService` — business rules
  (patient-number conflict detection, user-linkage validation) and
  **transaction ownership**. `create_patient` is this codebase's first
  real mutating transaction: it commits once every check has passed, and
  commits nothing at all if a check fails first (nothing was ever
  `add()`-ed, so there is no partial state to roll back — see
  `PatientService.create_patient`'s docstring). Reads
  (`get_patient`/`list_patients`/`get_own_patient_record`) never commit.

Authorization (*is this caller allowed to call this at all*) is decided
entirely at the FastAPI-dependency layer, before a route handler ever
calls into `PatientService` — see Section 8. `PatientService` answers a
narrower question: given an already-authorized request, is the DATA it
describes valid.

## 7. Date of Birth and Names

- `date_of_birth` is a `date`, not a `datetime` — no computed age is
  stored (age is always derivable from `date_of_birth` at read time by
  any caller that needs it; storing it would just be a value that goes
  stale). Validated, at both the API schema layer
  (`app.schemas.patient.PatientCreate`) and the model layer
  (`app.models.patient.Patient`, defense-in-depth for any non-API
  caller), to reject a value in the future. No further clinical/
  age-based rules are implemented.
- `first_name`/`last_name` are simple, required fields with modest
  whitespace normalization (trim + collapse internal runs of
  whitespace) — this is an **initial, administrative** representation,
  not an attempt at culturally universal name parsing.

## 8. Authorization Matrix

| Route | ADMIN | STAFF | PATIENT |
|---|---|---|---|
| `POST .../patients` (create) | allowed | allowed | 403 |
| `GET .../patients` (list) | allowed | allowed | 403 |
| `GET .../patients/{id}` | allowed | allowed | 403 |
| `GET .../patients/me` | allowed (see Section 9) | allowed (see Section 9) | allowed, own record only |

Every route requires, via FastAPI dependencies (`app.auth.dependencies`,
STORY-004): a valid Bearer token (`get_current_user`, 401 on failure), an
**active** `OrganizationMembership` in the `organization_id` path segment
resolved fresh from the database (`get_current_membership`, 403 on
missing/inactive), and — for create/list/get-by-id — a role of `ADMIN`
or `STAFF` specifically (`require_roles`, 403 otherwise). `organization_id`
and role are never trusted from the JWT — see [RBAC.md](RBAC.md) Section 4.

## 9. Patient Self-Access (`GET .../patients/me`)

Conceptually: *authenticated user* + *active membership in the target
organization* + *`Patient.user_id == authenticated user's id`* -> allowed,
scoped to exactly that one record.

**Decision: `ADMIN`/`STAFF` may also call `/patients/me`.** This is
explicit, not an oversight: the route only ever returns "the patient
record linked to the CALLER'S OWN `user_id`, in this organization" — it
cannot be used to inspect anyone else's record no matter the caller's
role. Given Section 4's linkage rule (linking requires an active
`Role.PATIENT` membership), an `ADMIN`/`STAFF` membership will, by
construction, almost never have a linked patient record — so this route
simply returns `404` for them. Gating it behind `require_roles(Role.PATIENT)`
instead would add a role check that changes no actual access outcome,
so it was deliberately left as "any active member" to keep the
dependency list minimal (`get_current_membership` alone).

A `PATIENT`-role membership **cannot** use `GET .../patients/{id}` to
inspect an arbitrary record by UUID — that route requires `ADMIN`/`STAFF`
(Section 8). Knowing a patient's UUID never grants access on its own.

## 10. Cross-Tenant Protection

`GET .../patients/{id}` and `GET .../patients/me` both resolve through
`app.repositories.patient`, which filters by `organization_id` in the
SQL `WHERE` clause itself (Section 5) — a patient that exists but
belongs to a **different** organization is, from the repository's return
value, indistinguishable from a patient that doesn't exist anywhere.
`PatientService` raises the identical `PatientNotFoundError` (404) in
both cases (`app.services.patient.PatientNotFoundError`'s docstring is
explicit about this) — a caller who knows a valid patient UUID belonging
to another organization gets exactly the same 404 as a caller who made
the UUID up. Verified in `tests/api/test_patient_endpoints.py`
(`test_cross_tenant_patient_lookup_returns_not_found`) and
`tests/services/test_patient.py`.

This mirrors the same non-disclosure principle STORY-004 established for
membership/role (see [RBAC.md](RBAC.md) Section 7) applied to a real
resource for the first time.

## 11. Error Model

Three application exceptions (`app.services.patient`), all mapped through
the existing global exception handling (`app.core.exceptions`) — never a
raw `IntegrityError`/driver exception reaching a client:

| Exception | Status | Meaning |
|---|---|---|
| `PatientNotFoundError` | 404 | No patient matches, within the caller's own organization (Section 10). |
| `PatientNumberConflictError` | 409 | `patient_number` already in use in this organization. |
| `InvalidPatientLinkError` | 422 | The requested `user_id` cannot be linked right now — no/inactive membership, wrong role, or already linked to a different patient in this organization (Section 4). Deliberately uniform across all four sub-reasons — see the class docstring. |

## 12. Data Minimization

`PatientResponse` (`app.schemas.patient`) exposes exactly the
administrative fields in Section 1's scope and nothing else: no
SQLAlchemy relationship objects (`organization`, `user`), no internal
DB state. There is currently no medical/clinical field anywhere in this
model to accidentally expose — this is enforced by what the model
doesn't contain, not by response-schema filtering alone.

## 13. Current vs. Planned

**Current (this story):** `Patient` persistence; organization-scoped
patient numbers; optional, validated `User` linkage; a tenant-scoped
repository and service; `POST/GET .../patients`, `GET .../patients/{id}`,
`GET .../patients/me`; the full authorization matrix (Section 8); the
first real mutating transaction pattern (Section 6).

**Explicitly not implemented in this story** (later stories): patient
update/delete; any diagnosis/symptom/medication/treatment/clinical-note/
insurance/emergency-triage data; `Department`, `Doctor`, `Appointment`,
`Document`; any workflow engine, agent, or LLM integration; public
patient registration; a patient-number generation engine; a frontend.
